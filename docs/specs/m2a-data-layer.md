# M2a — Data layer: schema, ledger, seed
Status: draft · Milestone: M2 (part a) · ADRs: 0001, 0003

## Problem
M2 needs auth, profiles, balances, and read-only market pages. Auth and the live database
wait on Supabase credentials the human holds, but everything below the UI can be built and
proven now: the full schema from architecture §7, the append-only ledger with its
zero-sum invariant, and the market read queries. Tests run against an in-process Postgres
(PGlite) so CI needs no database.

## Scope
In (`apps/web/src/db`, `apps/web/src/server`):
- Drizzle schema for every table in architecture §7: `profiles`, `settings`, `balances`,
  `categories`, `markets`, `trades`, `positions`, `ledger_entries`, `disputes`, `audit_log`,
  `price_snapshots`. Postgres enums or `CHECK`s for `role`, market `status`, `outcome`,
  `side`, `account_type`, `reason`, dispute `status`.
  - Points columns: `bigint` (`mode: "number"`). Contracts and `q_*`: `numeric(18,6)`.
    Probabilities: `double precision`. `b`: `integer` with `CHECK (b BETWEEN 50 AND 500)`.
  - Constraints: unique `(user_id, idempotency_key)` on trades; PK `(market_id, user_id)` on
    positions; unique `markets.slug`, `categories.slug`; index `markets(status, close_at)`;
    index `ledger_entries(account_type, account_id)`; index `price_snapshots(market_id, at)`.
  - `profiles.id` is a uuid with no FK to `auth.users` (keeps the schema portable to PGlite;
    the app creates the row on first sign-in in M2b).
- Migrations generated by `drizzle-kit generate` and committed, plus one custom SQL migration
  (`drizzle-kit generate --custom`) that:
  - enables Row Level Security on every table with no policies (deny-all for anon/authenticated);
  - adds triggers that raise on `UPDATE` or `DELETE` of `ledger_entries` and `trades`
    (append-only, enforced even for the owner role).
- `src/server/ledger.ts`:
  - `postTransfer(tx, { entries, reason, refType, refId })`: inserts balanced entries
    (rejects unless every delta is a safe integer and they sum to 0), and in the same
    transaction upserts `balances` for every `user` account touched.
  - `grantSignupBonus(tx, userId, points)`: `house → user`, reason `signup_bonus`, idempotent
    per user (a second call is a no-op).
  - `checkLedgerInvariants(db)`: returns `{ ledgerSum, mismatches: [{ userId, cached, ledger }] }`.
- `src/server/markets.ts` (read only): `listMarkets({ status?, categorySlug? })` and
  `getMarketBySlug(slug)` returning rows plus `probYes` and `displayPrice` computed with
  `@mc-kalshi/engine` from `b`, `q_yes`, `q_no` (numeric parsed once at the boundary).
- `src/db/seed.ts` + `npm run db:seed`: 4 categories (Campus Life, Academics, Weather,
  Clubs & Events — no athletics until open question 1 is answered) and 6 `open` markets with
  plain-English rules, `b = 100`, `q = (0, 0)`, close dates in the future. Idempotent
  (upsert on slug). Copy follows hard constraint 1 (no "bet", "$", "cash out").
- Test harness `src/db/test-db.ts`: fresh PGlite instance with all migrations applied, for
  Vitest only (not imported by app code).

Out: Supabase Auth, sign-in UI, profile creation flow, market pages (M2b); `placeTrade` (M3).

## Acceptance criteria
- [ ] `npm run db:generate` reports no pending changes after the committed migrations.
- [ ] Migrations apply cleanly to a fresh PGlite database (test).
- [ ] Inserting a market with `b = 49` or an unknown status fails (test).
- [ ] `UPDATE` and `DELETE` on `ledger_entries` and `trades` raise (test).
- [ ] `postTransfer` rejects unbalanced or non-integer entries and writes nothing (test).
- [ ] After a random sequence of transfers (fast-check), `ledgerSum = 0` and `mismatches = []` (test).
- [ ] `grantSignupBonus` twice for one user credits once (test).
- [ ] `listMarkets` / `getMarketBySlug` return `probYes = 0.5`, `displayPrice = 50` for a seeded market (test).
- [ ] Seed runs twice against PGlite without duplicates (test).
- [ ] `npm run typecheck && npm run lint && npm test && npm run build` green.

## Data touched
All tables created. Ledger reasons used: `signup_bonus` (others defined, used from M3).

## Risks / open questions
- PGlite vs Supabase Postgres differences (roles, `auth` schema): kept out of the schema; RLS
  and triggers are plain Postgres. Applying the migrations to the Supabase `dev` project is a
  human step (SOP-07) and is the real check.
- Real roles: the deny-all RLS assumes the app connects as the table owner (`postgres`), which
  bypasses RLS; verify against Supabase when credentials are in place.
