## Environment variables
Committed template `.env.example` (no values); real values in `.env.local` (gitignored) and in Vercel per environment.

| Variable | Scope | Purpose |
|---|---|---|
| `NEXT_PUBLIC_APP_URL` | public | optional and **currently unused**: the code never reads it (sign-in is an emailed 6-digit code, no link). Listed commented-out in `.env.example` in case a link flow is added |
| `NEXT_PUBLIC_SUPABASE_URL` | public | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | auth client key (the newer `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` also works and wins if both are set); tables are RLS deny-all so it reads nothing directly |
| `SUPABASE_SERVICE_ROLE_KEY` | server only | admin auth operations (never shipped to the browser) |
| `DATABASE_URL` | server only | Postgres connection for Drizzle (use the pooled connection string on Vercel). After ADR-0006's owner step it logs in as `mc_app`, not the owner. **In Production it must log in as `mc_app`**: on `VERCEL_ENV=production` the app asks `select current_user` on its first connection and refuses the database (one log line, `/api/health` reports `db: "error"`) for any other role |
| `POSTGRES_URL` | server only | set by Supabase's Vercel integration (pooled). The app uses it only when `DATABASE_URL` is unset; migrations and seeding use it last. Usually the owner string, so in Production set `DATABASE_URL` to the `mc_app` string rather than relying on it |
| `POSTGRES_URL_NON_POOLING` | migrations only | set by Supabase's Vercel integration (direct connection). Never used by the app at runtime; migrations and seeding use it after `MIGRATION_DATABASE_URL` and `DATABASE_URL` |
| `MIGRATION_DATABASE_URL` | local only, never on Vercel | optional; the owner (`postgres`) connection used by `db:migrate`, `db:studio` and `db:seed`. Needed once `DATABASE_URL` is `mc_app` (ADR-0006) |
| `DATABASE_CA_CERT` | server only | optional; Supabase CA certificate PEM (Project Settings → Database → SSL Configuration). When set, the DB connection verifies the server certificate; when unset, TLS without verification. Set it in Vercel (Preview and Production) and `.env.local` |
| `CRON_SECRET` | server only | shared secret checked by cron routes (M3) |
| (resolution order) | | one resolver, `apps/web/src/db/url.ts`: the app at runtime uses `DATABASE_URL`, else `POSTGRES_URL`; `drizzle.config.ts` and `db:seed` use `MIGRATION_DATABASE_URL`, else `DATABASE_URL`, else `POSTGRES_URL_NON_POOLING`, else `POSTGRES_URL`. Blank counts as unset. Sign-in counts as configured when the Supabase URL, a key (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` or `NEXT_PUBLIC_SUPABASE_ANON_KEY`) and a runtime database URL are set |
| `ALLOWED_EMAIL_DOMAINS` | server only | optional; defaults to the two college domains. The `hook_before_user_created` SQL has them hardcoded, so changing them also needs a migration (default `maryvillecollege.edu,my.maryvillecollege.edu`) |
| `TRADING_PAUSED` | server only | `true` freezes `placeTrade` (SOP-06; M3) |
| `STIPEND_POINTS_WEEKLY`, `SIGNUP_BONUS_POINTS`, `BALANCE_CAP_POINTS` | server only | economy knobs until a `settings` table exists |

Mapping: Vercel **Preview** → `mc-kalshi-dev` keys; Vercel **Production** → `mc-kalshi-prod` keys. Local `.env.local` → `dev`.

## Steps: first-time setup
1. Create the Supabase projects. In each: Auth → Providers → Email: enable, OTP on, "Confirm email" on; set Site URL and redirect URLs to the app URLs; enable the domain-allowlist auth hook, **in both `dev` and `prod`** (until enabled, non-college addresses can create `auth.users` rows and trigger emails; Authentication → Hooks → Before User Created → Postgres function `hook_before_user_created`, created by migration `0002_auth_signup_hook`; see `docs/specs/m2b-auth.md`), and edit the Magic Link email template to send `{{ .Token }}` (a 6-digit code, no link).
2. Copy keys into `.env.local` (dev) and into Vercel (Preview = dev, Production = prod). Never paste a key into chat, an issue, or a commit.
3. `npm ci`, `npm run db:migrate` against dev, `npm run db:seed` (categories + six sample markets), `npm run dev`, sign in with a test `@my.maryvillecollege.edu` address, confirm a non-college address is rejected.
4. Push a branch; confirm the Vercel preview builds and signs in against dev.
5. Run `npm run db:migrate` against prod only when releasing (SOP-05).

## Steps: new machine
1. Install Node 24 LTS (≥ 24.22.1), Git, Claude Code; clone the repo; `npm ci`.
2. Get `.env.local` values from the project lead through a password manager share, never email or chat.
3. `powershell -ExecutionPolicy Bypass -File scripts\setup-rea.ps1` only if REA research is planned on that machine.
4. Start Claude Code from the repo root; follow SOP-01.

## Steps: rotate a secret
1. Generate the new value in the provider (Supabase: Settings → API → rotate; `CRON_SECRET`: `openssl rand -hex 32`).
2. Update Vercel (both environments if shared) and `.env.local`; redeploy production.
3. Confirm sign-in and one 10-point trade on prod; confirm the cron route returns 200 with the new secret.
4. Record the rotation (date, variable, reason) in `docs/incidents/` if it was a leak, otherwise in the CHANGELOG. The repo is public: never include the leaked value or any user identifier.

## Checks
- `git grep -n "SUPABASE_SERVICE_ROLE_KEY\|DATABASE_URL" -- ':!.env.example' ':!docs'` returns only code that reads `process.env`.
- `.env.example` lists every variable the code reads (CI greps for mismatches once M0 adds the check).
- The anon key cannot read any table: `select * from markets` through the anon client returns zero rows.
